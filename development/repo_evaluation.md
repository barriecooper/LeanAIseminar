# Lean + AI seminar repository evaluation

22 November 2026 · University of Exeter, Mathematics and Statistics

Reviewed commit `0643940`, which pins Lean and Mathlib to `v4.37.0-rc1`.

## Overall assessment

The repository is a good basis for a first encounter with Lean, but its choice of examples makes the seminar feel more like an introduction to formalising elementary number theory than an introduction for a broad Mathematics and Statistics department. The strongest choices for that wider audience are the first arithmetic comparison, induction as a way to prove an invariant, and Euclid as a demonstration of algorithm instrumentation. The full worksheet is too ambitious as a hands-on target for 50 minutes with a news opening and first-time Codespaces setup. The [workshop brief](../WORKSHOP_BRIEF.md) already allocates every minute and assumes participants can use Infoview from minute zero.

Keep the existing sequence and use three outcomes to define a successful session. Participants should change an input and predict the output, complete a small proof and watch its goal close, and explain what stays the same when they change Euclid’s observer. This gives colleagues across pure mathematics, statistics and applied mathematics a common experience without assuming programming or specialist number theory.

For the core exercises, Lean should be the only unfamiliar ingredient. A participant should be able to explain the task in plain language and predict the result by hand before editing code, using the mathematics and Lean notation already introduced. Set the same bar for programming concepts. If reading the exercise requires knowing how a generic interface works, the exercise needs a simpler entry point.

## Choice of topics for this audience

- **Integer division and divisibility earn their place as the opening.** The arithmetic is familiar enough for the room to concentrate on what Lean is doing. Integer and rational division also give a concrete reason for applied mathematicians and statisticians to care about types. One explicit divisibility witness is enough to introduce proof construction. More divisibility theorems give diminishing returns before anyone has seen a use closer to their own work.
- **Modular arithmetic earns a short appearance for library reuse.** Remainders are accessible, and finding an existing theorem in Mathlib is a transferable skill. The ring homomorphism material spends time on algebraic terminology that the rest of the core session barely uses. Keep one residue calculation and one library lookup, then make the homomorphism material an optional algebra example.
- **Recursion and induction are the most transferable mathematical topics.** The parity example is simple enough to work through by hand. Its value for this audience is the pattern of proving that an update preserves a property at every step. The same question arises when an iterative numerical method needs to maintain a valid state or when a data-processing routine updates a running summary. Make that connection explicit when the induction hypothesis appears.
- **Collatz is the easiest topic to compress.** Its surprising trajectories make an engaging demonstration of how much can happen under a simple update rule. The distinction between inspecting sample trajectories and proving a one-step property is worth keeping. A longer Collatz exercise repeats the recurrence activity and adds a second block of modular arithmetic. Keep it as a brief experiment and make the modulo-four proof a stretch exercise.
- **Keep observable Euclid as the finale and make instrumentation the subject.** Changing from a count to a trace while preserving the GCD shows a guarantee about two ways of running an algorithm. That is relevant to people who inspect solver iterations or record diagnostics in simulations. The GCD is a manageable example because the room can check the divisions by hand. Continued fractions add specialist content with little payoff for that learning objective.

**Give statistics an explicit example.** The worksheet has no task framed around data or statistical computation. A two-minute transfer example after Euclid would fill that gap without adding new Lean syntax. Picture a routine that reads a column and sums the observed values. One diagnostic counts skipped missing values and another records their row numbers. With the same input and missing-value rule, both runs should return the same sum. Ask the room to identify the result, the two diagnostics and the assumptions that make the comparison meaningful. This illustrates the kind of guarantee Lean can express about a statistical workflow using only the ideas participants have just seen. If one topic is dropped to make time, shorten Collatz first.

### Coercions and event observers

**Coercions are too much for a required first-session task.** In the opening division example, `(13 : Int)` and `(13 : Rat)` tell Lean which type to use for a numeral. In `((13 : Int) : ZMod 7)`, the inner annotation fixes the numeral as an integer and the outer one makes Lean insert a conversion. The worksheet uses the same notation for both ideas and soon asks readers to follow a ring homomorphism. A participant who understands remainders can still get stuck working out what Lean converted and why. Use `#eval (13 : Int) % 7` for the core remainder exercise and the existing divisibility example for library search. If showing `ZMod 7`, demonstrate one conversion after the remainder example and make reading or writing casts and homomorphism proofs optional.

**The observer idea belongs in the core. The `EventObserver` interface belongs in follow-up.** The question “Would recording each division change the answer?” is accessible once the presenters show the division steps. The existing `runEuclid (countObserver EuclidEvent)` calls ask participants to read a generic observer argument before they have seen what the observer does. The interface itself requires reading a structure whose `State` field is a type, then following an update function and a return type that depends on the chosen observer. Those are substantial new programming concepts for the last ten minutes.

Start with `#eval euclidCount 35 15` and `#eval euclidTrace 35 15`. Work through the two divisions by hand, predict the GCD and count, and let participants change the two inputs. Read the first component of both outputs as the GCD and the second as either the number of emitted division events or the chronological list of those events. Present observer independence in plain English as a guarantee for all inputs. Offer the `EventObserver` definition, the raw reversed trace and the formal proof to participants who want to see how the guarantee is implemented.

## Suggested 50-minute run of show

| Minutes | Activity |
| --- | --- |
| 0–7 | Launch the browser workflow from a projected link. One presenter gives the Lean and AI opening while the other helps with GitHub sign-in, branch selection and setup. |
| 7–17 | Read a type, predict and edit an evaluation, then close the first `sorry`. Briefly show a divisibility witness if the room is ready. |
| 17–23 | Calculate a remainder with `%` and demonstrate a library lookup. Use this slot for a short AI demonstration. |
| 23–32 | Compare the two recurrences and read an induction goal. Offer the scaffolded oddness proof to early finishers. |
| 32–36 | Change a Collatz input and compare observations with the statement of the one-step theorem. |
| 36–47 | Predict and compare Euclid’s count and chronological trace. Read the observer-independence statement in plain English, then apply the idea to the missing-value example. |
| 47–50 | Ask participants to explain the difference between evaluating examples and checking a general proof. Point to solutions and optional exercises. |

Keep the opening short enough that late arrivals can still catch the first edit. If using Verso, a few browser-ready slides suffice. Show the recent result, display a small goal in Infoview, and leave the launch link and first task visible. As of 22 November, the Lean and Mathlib communities reported that their checks confirmed both Alpöge’s Claude-assisted proof and its match to Mathlib’s statement of the Riemann Hypothesis. Clay still listed the problem under **Unsolved problems** on its prize page. Attribute both statuses and refresh them before the seminar. Use the worksheet to show what that means in practice. Lean checks a proof of a precise statement, and people still need to understand the statement and explain the argument. [Alpöge’s announcement](https://alpo.ge/remark.pdf) · [Lean and Mathlib verification](https://leanprover-community.github.io/blog/posts/riemann-hypothesis/) · [Clay’s prize status](https://www.claymath.org/millennium-problems/)

Give AI one visible role early. Use the divisibility example with hypothesis `h : x ∣ y - z` and goal `x ∣ z - y`. Ask an assistant to explain the goal in plain English and suggest one Lean proof step using the existing imports and pinned version. Compare the suggestion with Lean’s `apply?` result and try it in the editor. Have the presenters run this once so participants can follow without an AI account. The advanced GCD prompts already give a good model for breaking a larger proof into small questions.

## Browser readiness and delivery risks

1. **Align the README with the launch route.** The current badge opens the upstream repository. If participants should fork first, give them the browser steps **Fork → Create fork → Code → Codespaces → Create codespace**, plus the exact workshop branch. The updated pin was one commit ahead of the local `origin/gihan_version` tracking ref at review time. Confirm the intended revision is published and appears in a fresh participant fork. If saving or publishing work to a fork is unnecessary in the session, the direct launch reduces friction. GitHub documents opening a Codespace before forking when the user has permission to fork. [README launch instructions](../README.md#lean--ai-workshop) · [GitHub’s automatic forking guidance](https://docs.github.com/en/codespaces/developing-in-a-codespace/using-source-control-in-your-codespace#about-automatic-forking)
2. **Update the version and cache guidance together.** The README still says `v4.24.0`. The cache client at the new Mathlib pin uses `cache.mathlib.org` and no longer reads `USE_FRO_CACHE`, so the documented mirror switch and setup failure advice are stale. The setup script’s targeted cache request, availability check and stage timings are worth retaining. Verify a cold setup against the selected commit before relying on the new release candidate in the seminar. [Setup script](../.devcontainer/setup.sh#L35) · [Pinned Mathlib cache documentation](https://github.com/leanprover-community/mathlib4/blob/31ce06eaadf4a200c0e1407c5f10953cf606b8f8/Cache/README.md#public-cache-endpoint)
3. **Rehearse as a participant from a fresh fork.** Time sign-in through the first visible `#eval` in VS Code for the Web, confirm the tutorial opens and Infoview shows a goal, then replace the first `sorry`. Test from the intended account type and network. If relying on a prebuild, confirm it is offered on that launch route. Ask attendees to check GitHub sign-in and Codespaces access in advance. If a participant is still waiting at minute seven, have them work alongside a neighbour or follow the presenter’s ready Codespace until theirs comes up.
